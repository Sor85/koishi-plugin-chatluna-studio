# 客户端 RPC 按能力拆成三道端口，而不是喂一个大工作区端口

客户端有三道 Console RPC 端口，每道都是三件套：类型化 interface（`port.ts`）、Koishi 适配器（`koishi-port.ts`）、内存假实现（`fake-port.ts`）。三道分别是工作区（`client/workspace/`）、模型请求（`client/model-request/`）、预设（`client/preset/`）。

判据是「输入里有没有对方的概念」。工作区端口一个入参都没有——它取的是外观与持久化状态这类全局事实；模型请求端口的输入里是范围、游标与记录标识；预设端口的输入里是文档种类、文件名与修订。三者互不出现在对方的入参里，塞进一个 interface 只会让它承担三个互不相关的变更原因。

代价是调用方要认识三个 seam，换来的是每个假实现只覆盖自己那一类能力——手写假端口的体积不随能力总数增长，这是继续喂大端口时最先失控的东西。工作室 shell 的全部跨区域规则（切视图、脏值守卫、证据跳转）因此可以在三个内存替身上被完整驱动，不需要浏览器也不需要 Koishi。

广播订阅归工作区端口而不是模型请求端口：一份广播扇出给多少个页面、以及只向 Koishi 注册一次底层回调，都是传输层的事，与「读哪一页记录」不在同一个关注点上。Koishi 的 `receive` 对同名事件只保存一个回调，页面反复挂载时若每次都注册，后卸载的页面会留下失效回调并覆盖存活页面；适配器只注册一次再扇出，这条规则因此有唯一持有者。
