# 滚动视口顶边的子像素接缝由 pane 上的遮盖条压住

模型请求详情外壳（`.chatluna-studio-model-request-detail`，`overflow: auto`）的顶边落在分数 CSS 像素上——布局链上游的页面标题行高度带小数（实测值形如 66.09375px），于是滚动视口顶边是 179.09375px 这类分数值，DPR 2 时对应 358.1875 设备像素。吸顶的轨迹头部是 `position: sticky`，被提升成独立合成层；它与滚动内容层各自把这条分数边界取整到不同的设备像素行，裁剪边上因此漏出一行滚动正文。遮盖条挂在滚动容器**外面**的 `.chatluna-studio-model-request-detail-pane` 上，用 `::after` 覆盖顶部三像素，不参与那两层的取整。

**吸顶头部的毛玻璃必须保留，不得为了压这条接缝把它改成实心。** 这一点是踩过坑的：排查时曾判定「Firefox 不执行 `::before` 上的 `backdrop-filter`」，据此把这个头部改成实心表面，结果毛玻璃没了而接缝照旧。那个判定是错的，成因见下一段——真实 Firefox 里模糊工作正常，退化的是验证手段。头部的背景层与模糊本身收敛在 `.chatluna-studio-overlay-header` 的共享 `::before` 上（见 [ADR-0019](./0019-restrict-backdrop-filter-to-floating-surfaces.md)），组件局部的 `::before` 只补自己的分隔线。

**`page.screenshot` 拿不到 GPU 合成结果，因此它对 `backdrop-filter` 和这条接缝同时给出错误答案。** Playwright 的截图走渲染器的绘制路径；`backdrop-filter` 是合成阶段的操作，在那条路径上根本不执行，于是自动化截图里毛玻璃看起来「完全失效」，而合成阶段产生的接缝看起来「根本不存在」。两个方向的误判都源自同一个盲区：在 Firefox 与 Chromium 下、DPR 1 与 2、多种视口、多个滚动位置上，对头部整块及其上下边缘、乃至跨越裁剪边 ±2px 的窄窗口做「正文可见 / 正文隐藏」逐字节比对，差异一律是 0，而同一时刻真实浏览器窗口里那行字清晰可见。**验证毛玻璃、混合模式、`backdrop-filter`、合成层接缝这类现象，必须用真实截屏工具或肉眼，不要相信自动化截图的比对结果。** 顺带一条：正常工作的毛玻璃表头本来就会透出背后内容的模糊痕迹，逐字节比对出现差异是设计意图，不能当成泄露的证据。

定位这条接缝落在裁剪边上，靠的是给头部加 `outline: 2px solid red` 后接缝被红线覆盖——也就是说它在头部边框外两像素以内。

**遮盖条不能挂进详情外壳自身。** 挂在 `.chatluna-studio-model-request-detail` 上的任何元素（包括 `position: sticky` 的）都在同一个滚动层里，会跟着接缝一起取整，压不住；`contain: paint` 同理无效——裁剪在绘制阶段本来就被遵守，问题发生在之后。pane 是滚动容器的父级、自身不滚动，是最近的一个不受影响的位置。左右各让出 17px（详情外壳的 16px 内边距加详情面板自身 1px 边框），否则这条横贯的遮盖条会在面板左右边框上切出一个三像素缺口；让出之后它的横向范围正好等于吸顶头部的盒子。颜色取 `var(--chatluna-studio-surface)`，与 pane 的背景同源，明暗两套主题都自动一致；而滚动视口顶部三像素在任何状态下都是纯表面（分析态是吸顶头部的背景，其余状态是详情外壳的顶部留白），所以遮盖条在任何滚动位置都不可见。

代价是这是按住症状而不是消除成因：浏览器仍然在那条边上漏，我们只是在它上面盖了一层不参与滚动的实色，而遮盖条的高度（3px）是个经验值，换设备像素比或换布局导致接缝变宽时它可能不够。真正消除成因的做法是像轨迹视图那样让头部 `position: absolute`、滚动交给内部容器（见 `client/model-request/styles.css` 的 `.is-trajectory-view` 一组规则），头部根本不进滚动层。那要求分析模式下的详情外壳改成固定高度，概览、用量、关联实体三块不再随正文滚动，是一次可见的信息取舍，因此没有在这次一并做掉。接缝若再次冒头，优先考虑那条路，而不是继续加高遮盖条。
