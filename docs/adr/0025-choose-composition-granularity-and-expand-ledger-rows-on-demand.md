# 会话轨迹按可辨识度选组成粒度，账本事件行按请求展开

一次逻辑会话里第 N 条模型请求的请求体本身就包含前 N 轮历史，因此按记录逐条投影会让会话轨迹的账本行与组成分段按记录数平方增长。以每轮一次工具往返、十二个工具定义的会话实测：五十条记录得到 6,925 行与 6,825 段、2.56 MB 载荷，一百条 26,350 行、9.81 MB，撞到 200 条聚合上限时 102,700 行、102,300 段、38.4 MB，其中序列化与反序列化各占 0.1 秒以上。载荷之外还有两处放大：每条分段各自挂一个浮层组件，十万个组件的挂载成本远超 DOM 本身；账本一次性渲染全部行，约三十万个节点。进行中的请求会让自动刷新每两秒把这一整套重做一遍。

组成分段改为两档粒度，由几何判据而不是记录条数决定。逐条证据粒度保持原样；挤不开时折成「每请求 × 每种类」一段，字符数只做加总，因此同一档在两种粒度下的占比完全相等，切换粒度不会让轨道厚度发生变化。判据取两种横轴布局里宽的那个——按实际耗时铺开时槽宽由耗时决定，按次序均分时每格恒为 `1/请求数`，用户随时可以切换，只按其中一种判会让另一种布局白白丢掉细节；时间槽占比先按总量归一，几条请求的跨度重叠时它们一起退回均分宽度，也就是真正能分到的空间。阈值按最大缩放倍率折算，因此「放大就能看清」的会话仍然逐条下发，聚合不会拿走用户本来够得到的细节。分段的最小宽度同时改成不再把分段撑得比真实占比宽：撑宽会让同一时间槽里的分段互相压住，读出来的厚度比真实占比大出好几倍。

账本的事件行改为按请求向服务端取，会话模式默认全折叠，只下发请求边界行。默认展开哪一条属于视图状态：详情视图在进入账本时播种当前请求一次，服务端只按清单下发、不替调用方补任何一条。这条边界是必须的——服务端补上的那一条会永远折不起来，用户点箭头、客户端把它移出清单、下一次读取又把它加回来，界面纹丝不动。返回定位不依赖那次补齐：视图快照自带当时的展开清单，而能被选中的行一定属于已展开的请求。展开清单同时是显示状态和读取参数，六个轨迹读取发起点全部经由同一处取参，否则自动刷新一到就会把展开的请求收回去。它进入详情视图快照，打开原始请求再返回时一起恢复；换记录时清空，否则会带着上一条会话的请求标识去取事件行。会话模式因此不再提供「全部展开」总开关——那等于把整段会话重新拉回来。同一份实测数据改造后：两百条记录 1,210 行、998 段、0.458 MB，二十五条以上一律走聚合粒度，十条以内仍是逐条证据。

展开与折叠的交互延迟由两处非数据成本主导，两处都改掉了。整条轨道共用一个分段浮层，而不是每条分段各挂一个 Tooltip 组件：一条 18 次请求的会话有 1,206 条分段，逐段挂载时每次重新取回轨迹都要让这 1,206 个组件重渲染一遍，实测点击展开的 269 ms 里有 224 ms 花在这上面，而服务端往返只占 45 ms。共用浮层之后分段退回普通按钮，落点几何与「首次悬停等一拍、开着时立刻换目标」的时序下沉成可单测的 module，键盘聚焦仍然显示浮层并保留 `aria-describedby` 关联。轨迹载荷同时改成浅引用加 `markRaw`：它只被整份替换，深响应式等于为上千条分段各建一个只读代理却没有任何一次写入。两处合计把点击到界面更新从 267~296 ms 降到 57~81 ms，其中渲染部分从 224~233 ms 降到 8~12 ms，剩下的是服务端往返，属于记录投影缓存要解决的部分。这条决定与「前端优先使用 shadcn 组件」冲突，冲突范围仅限组成图分段：一屏上千个浮层触发器是这条规则没有覆盖的量级，因此用一条否定式守卫钉住「不得再逐段挂 Tooltip」，并在守卫注释里写明少了它的表现形态是点击延迟回到两百多毫秒。

三处代价是显式接受的。聚合段覆盖一整档证据、没有单一证据身份，点击因此从「定位到那条证据」变成「展开这条请求并选中它」，精确定位下沉到展开后的账本；判定选中也相应从证据身份改成「请求 + 轨道」。账本搜索只覆盖已下发的行，会话模式折叠期间搜不到折叠请求内部的内容——服务端已经握有整段投影，把查询下推是自然的下一步，但它每次按键都要重投影整段会话，应当等记录投影缓存落地之后再做。服务端派生成本没有变化：折叠的请求同样走完投影，因为事件总数与组成占比是整段会话的事实，不随展开与否变化，省掉的是行对象与它们的预览文本，也就是载荷本身。

服务端选粒度之外还需要客户端按当前像素再合并一次，两者解决的是不同的问题。判据按最大缩放倍率折算，因此「放大就能看清」的会话仍然逐条下发；代价是默认倍率下那一屏读不出来——整段会话铺在一屏里时一条请求只分到几十个像素，它内部的几十条证据无论怎么算占比都落不到一个像素上，各自兜住像素级最小宽度之后互相压住。一条 18 次请求的会话实测：三条轨道上 1,159 处相邻分段重叠，最宽的分段也只有 2 px，也就是没有一段是按真实占比画出来的，整条请求糊成一根实心条，读出来的既不是占比也不是条数。因此投影之后多一步几何合并：相邻且同属一条请求的分段一路并到够宽为止，合成块覆盖首段左边界到末段右边界，占比读数不变，变化的只是「这一块里有几条证据」这一层细节。合并按当前实际画出来的像素判定，所以放大到一条请求时同一批分段自动散开，不必重新取一份投影。同一份会话实测：整段铺开时重叠从 1,159 处降到 4 处，放大到一条请求后为 0 处。两层的分工是服务端判据决定传什么、客户端合并决定画什么，谁都替代不了谁——只做客户端合并仍然要把 38 MB 传下来，只做服务端判据则默认倍率下的一屏照旧糊成实心条。合并只作用于会话轨道：单请求视图里一条请求独占整条轴，分段本来就够宽。

合成块保留它合了哪几条证据。它与服务端聚合段的区别正在这里：聚合是在下发之前折掉身份，合并只是把挤不开的相邻分段画成一块，合了哪几条始终是已知的。因此选中判定按成员判、点击落点取其中第一条，两者都精确到单条证据。曾经让合成块借用聚合段的「请求 + 轨道」判据，代价立刻显形：一条放大到单条请求、十几个工具声明的轨道上点中一个声明，同一轨道上另外三块合成块一起描边，因为它们各自只覆盖这一档里的几条、却按整档来判。落点同理——退回「展开这条请求」会让已经展开的那条请求点不出任何变化。会话模式只给展开的请求下发事件行，因此分段自带证据身份但那条请求还折叠着时，落点仍然是展开这条请求并选中边界行，精确定位随事件行到达后成立。

合并的边界有两条，都是「合并只能拿走细节、不能拿走事实」的直接推论。跨请求不合并：请求边界是这张图的横轴刻度。跨变量档不合并：变量片段落在 User 轨道上却自带一档颜色，把它与前后的普通 User 内容并成一块会让那一档颜色整块消失，读图的人看到的是「这条请求没有变量」而不是「变量太薄」——实测里那一块从紫红整块变回 User 蓝，正是这个形态。相邻的不同变量之间照旧合并：它们本来就是同一档颜色，丢掉的「这一块里是哪几个变量」与丢掉「有几条证据」是同一层细节，因此合成块保留变量档身份、只在整块同名时才报变量名，浮层与无障碍名也相应按变量档报而不是按它落在哪条轨道报。代价是显式接受的：一条 User 消息被十几个变量切开时，变量与普通内容交替出现，两者都挤不开也都不能相互合并，那一档在整段会话的尺度上仍然是一簇几像素宽的混色小块——变量的存在看得见，具体切分要放大才读得出。

分段之间那一份间隙同样收在一处换算，口径是「占所在那一格的百分比」而不是占整条轴。写成占整条轴的绝对值时，会话轨道的间隙会随请求数一起缩到看不见，而下限又按未扣间隙的占比兜——一格里的分段绝大多数都薄于下限，于是下限把刚扣出来的间隙原样填回去，间隙在会话轨道上全程失效。改成相对那一格之后，焦点窗口把一格拉到全宽得到的正是单请求视图里的那条轨道，这也是焦点窗口那条「读法完全一致」的承诺唯一成立的前提。真正一个像素宽的缝无法用占比表达，它由分段自身让出的一条透明右边框承担，两种模式共用同一份声明。

焦点窗口里「该画哪几条请求」按身份判，几何只负责把留下来的那几条裁进窗口。窗口端点取时间槽的左右缘，而分段端点由「格左 + 格宽 × 格内占比」连乘求得，两串运算指向同一个刻度却会差出几个 ULP；一条请求只占整段会话百分之零点几时投影倍率上百，那 1e-15 被放成一条能画出来的正宽度，再被分段的像素级最小宽度撑成一枚短桩。实测形态是「只展开一条请求，窗口左缘却露出前一条请求的一块工具声明」——工具声明是请求体的末尾一档，前一格的末段正好结束在窗口起点上。只按几何判还有一处分不开：进行中的请求在时间轴上是一格零宽的槽（它只标出起点），零宽槽贴在窗口端点上时，几何无从分辨它是窗口自己的边界还是邻格被顶到了边上，而两种情形一个必须画、一个必须不画。因此规则是展开的请求恒画、没展开的请求要在窗口内真的占到一段宽度才画，夹在并集中间的那几条满足后者；几何这一侧另留一份浮点噪声余量，把「贴着边缘但没有落进窗口」与「真的跨过边缘」分开，余量与真实的细分段之间仍有六个数量级。

不采用三种更省事的做法。按记录条数设硬阈值不成立：同样二十条记录，每条几百段与每条几段的可辨识度差两个数量级，而条数看不出这个差别。只在客户端折叠分段不解决传输，38 MB 仍然要序列化、下发、反序列化一遍——它治的是可辨识度，因此留作上面那一层，而不是粒度判据的替代品。只做账本虚拟滚动同样不解决传输：它治的是「画不画」而不是「传不传」，而账本行占该载荷的近七成。
